# Architecture

This file explains how the code in `dykstra/` is put together, and which of its properties are contracts rather than accidents. `AGENTS.md` is the shorter operating guide, with the environment, the commands, the conventions, and the command behind every figure and table. Read that first, and this when you are about to change something.

## 1. Scope and nongoals

The repository is research code behind a paper. It is not a library: it does not have an installer, a stable API, or versions. `dykstra/` is a package only so that its modules import one another by absolute name, as in `from dykstra.lti_solver import LTIVer5Solver`, and it runs from the repository root without being installed. Its callers are the figure and table scripts inside it, the interactive examples `main.py`, `paper_figure.py`, and the LTI runners, and the test suite.

The numerics are dimension-agnostic, and the dimension comes from the point being projected. The visualisation layer is 2-D only and always will be, because its job is to show geometry a reader can see. Do not try to generalise the visualisers. Add a different output instead.

## 2. The problem

The task is to project a point $z$ onto $\{x : Ax \le b\}$, the intersection of finitely many half-spaces.

The method of alternating projections (MAP) converges to some point of the intersection. Dykstra's algorithm converges to the projection, by carrying a correction vector per constraint and subtracting it before each projection. This difference is the reason the repository exists.

On a polyhedron Dykstra's algorithm can stall. Over a stalling period the iterate does not move while the corrections of some half-spaces keep changing, and then it moves again. In the paper, such a fixed iterate is called a stationary state, a run of cycles whose squared error repeats on the rounding grid an approximate stall, and a long stretch of slow geometric convergence a slow phase. The stall detection solver skips a stalling period in one step. The paper's accelerated solver goes further and compacts every run of cycles with a constant active set, which is what the LTI solvers implement. The paper is the long version of this section.

## 3. Module graph

An arrow points from a module to the modules that import it.

```
          quadprog
             │
        gradient.py          projection_result.py
             │                 │              │
             v                 v              v
       convex_projection_solver.py        visualiser.py ──> CSV via ResultExporter
        │            │            │
        v            v            v
  lti_solver.py   oracle.py   c_solvers.py ──> C/ libraries through ctypes
        ^            ^
        └── lti_numerics.py
```

The LTI solvers sit beside the core solvers rather than inside them. `lti_solver.py` subclasses `ConvexProjectionSolver` and draws its numerics from `lti_numerics.py`, which does not hold any solver state. `oracle.py` draws on `lti_numerics.py` but not on `lti_solver.py`. Both also import `projection_result.py`. `c_solvers.py` calls the base class's `_validate_problem` before handing a problem to the C libraries.

`convex_projection_solver.py` holds the algorithms and does not import any plotting. `projection_result.py` is a dataclass and does not import any other module of the package. `visualiser.py` reads a `ProjectionResult` and the constraint arrays and never calls a solver. `gradient.py` wraps `quadprog`, and that library is not imported directly by any other module. `edge_rounder.py` produces constraint arrays and is optional, since only a regression test and commented-out lines of `main.py` import it.

The figure and table scripts sit on top. `problem_generators.py` draws every random problem, i.e. the polyhedra of the supplement and the wedge and stall families of the benchmark, and `paper_figures.py` defines the output folder, the palette, `save_figure`, and `save_tex`, through which every other figure and table script writes. `performance_timing.py` defines `machine_description`, which `benchmark.py` and `cost_model.py` reuse. `stall_angles.py` runs plain Dykstra through `stall_grid.run_batch` and draws its wedge from `problem_generators.py`, and `activity_study.py` records its runs and leaves the drawing to `activity_figures.py`. `cost_model.py` profiles `LTIVer5Solver` and times the C solvers on the problems of `performance_timing.py`, and `compaction_only.py` runs the accelerated solvers of both languages under the schedule `"never"` and checks the stall length with the functions of `square_line_example.py` and `stall_grid.run_batch`. `activity_conjecture.py` depends only on `paper_figures.py` and on `lti_numerics.rounding_floor`, since it runs its own vectorised and exact Dykstra cycles on three half-planes. `singular_phases.py` records the curve battery of `activity_study.py` with that module's own functions and the dense tiers with `oracle.record_schedule`, and `oracle_comparison.py` runs the projection methods of `benchmark.py` beside a profiled `LTIVer5Solver`. The interactive examples `main.py` and `paper_figure.py` and the `run_*.py` runners call the solvers and the visualisers, and `lti_examples.py` holds the box-and-line example that the runners and `tests/test_stress_lti.py` share.

Every import is an absolute package import. `dykstra/__init__.py` defines `REPOSITORY_ROOT`, the folder that contains `dykstra/`, and does not import any of the modules. `c_solvers.C_FOLDER` is `C` under `REPOSITORY_ROOT`, and `paper_figures.OUTPUT_DIR` is `results/paper` under it, so the libraries and the outputs are found whatever the working directory. The repository root must still be the working directory of `python -m`, because the package is not installed (`package = false` under `[tool.uv]` in `pyproject.toml`).

## 4. The solver hierarchy

`ConvexProjectionSolver` is an abstract base class holding two distinct things.

The geometry is a set of static methods, free of dependencies and testable one by one. `_normalise` scales a normal to unit length and its offset with it. `_project_onto_unit_half_space` projects with such a pair, forming the product of the point and the normal once, and `_project_onto_half_space` normalises first and then calls it. The others are `_is_in_half_space`, `_validate_problem`, `_find_optimal_solution` (the QP reference, through `gradient.py`), `_beta_check` (whether the point lies inside the whole intersection, given the normalised pairs), and `_delete_inactive_half_spaces`, which is retained only so that a test can prove it keeps every constraint.

The constructor validates the problem and stores `unit_constraints`, one pair of unit normal and normalised offset per row, which every visit projects with. They are computed row by row by `_normalise`, since `np.linalg.norm` along axis 1 sums the squares in another order and would change the last bit of every result. The constructor then computes the reference projection and calls `_reset_state`.

The tracking scaffolding is a set of instance methods: `_reset_state`, `_initialize_iteration`, `_check_activity`, `_track_activity`, `_track_error`, and `_update_error`. `_reset_state` sets the iterate, the corrections, and every record back to cycle 0 in fresh arrays, of `max_iter + 1` cycles because the initial state is cycle 0. Every `solve()` calls it first, so a second call starts afresh and leaves the arrays of the first result alone. `_track_activity` returns at once unless `plot_active_halfspaces` is set, since the activity record is read only by `_format_output`.

The three concrete solvers are listed below.

- `DykstraProjectionSolver` is the standard cyclic method and the reference implementation. Its `_update_error` is `e[m] = e[index] + (x_temp - x)`, and setting that coefficient to zero would turn it into MAP.
- `DykstraMapHybridSolver` keeps two sets of correction vectors, `e_dykstra` and `e_MAP`. At the top of each cycle `_initialize_iteration` selects between them with `_beta_check`: Dykstra's corrections while the iterate is inside the intersection, and zeroed MAP corrections while it is outside. Only the Dykstra set is ever updated. A point projected onto a boundary lies in its half-space only to rounding, hence `_beta_check` counts a point as inside when every normalised slack is at most `RELATIVE_TOLERANCE` (1e-10) of the magnitudes summed in it. The hybrid converges slowly on larger problems, and its limit is asserted only in two and three dimensions.
- `DykstraStallDetectionSolver` implements the fast-forward of [Vestini and Kempf 2025](https://doi.org/10.48550/arXiv.2511.18132). It flags a stall when the last `n` visits, one per constraint and possibly straddling a cycle boundary, all repeated their outputs from one cycle earlier. A visit counts as repeated when each coordinate of its output lies within a rounding floor of the previous cycle's. The floor is 64 eps times the magnitudes summed in the visit, i.e. the input, the correction, and the step along the unit normal, as in `lti_numerics.py`, so a stall whose outputs jitter in the last bit is caught at any scale. One repeating visit is not enough, because a cycle that repeats only in part would trigger jumps that plain Dykstra never makes.

While a stall lasts in the stall detection solver, an active half-space's scalar `d_m = e_m . a_m` changes by its constant slack `s_m = a_m^T x_{m-1} - b_m` on every visit, and the half-space first lets the point move on visit `floor(d_m / -s_m) + 1`. A ratio within rounding of an integer `k` is a tie, at which visit `k` gives the same point in either branch, and it counts as `k + 1` whichever way it rounded. `_handle_stalling` takes `N` as the least of these counts over the half-spaces active at their last visit with `s_m < 0`, advances every correction vector by `N - 1` cycles at once, and lets the switching cycle run normally. It does not jump when the auxiliaries of all active half-spaces stay level or grow, or when a half-space inactive at its last visit moved its input by more than rounding, since that half-space has just switched off and the cycle will not repeat. It does not jump either when `N` exceeds `MAX_SKIP_CYCLES`, i.e. `1/sqrt(eps)` or about 6.7e7. Beyond that, plain Dykstra's per-cycle rounding of `e_m` is as large as the decrease, and at a converged fixed point the slacks are rounding noise that would ask for about 1e16 cycles. The jump reaches the state plain Dykstra reaches after the skipped cycles, so only the path is shortened and the limit is untouched, which `tests/test_solver_regressions.py` checks cycle for cycle. The solver keeps `unit_A` and `unit_b`, normalised along axis 1, for its floors and slacks, while its visits project with `unit_constraints`, because merging the two would change the last bit of one or the other. It prints a line when it fast-forwards.

The extension contract for a fourth variant is to subclass `ConvexProjectionSolver`, override `_update_error`, `solve`, and `_format_output`, start `solve()` with `_reset_state()`, and preserve the invariant every variant shares, that one cycle projects onto every constraint once in the order the rows of `A` are given. Shared geometry goes on the base class, not into the subclass.

`dykstra_projection()` at the bottom of the module is a wrapper kept for backwards compatibility that returns the old five-tuple. New code calls the solver classes.

### The LTI solvers

`LTISolver` in `lti_solver.py` accelerates Dykstra's algorithm by treating it, between changes of the active set, as a linear time-invariant system, the reformulation and accelerated algorithm of the paper. It is one class with five presets, `cycle_map`, `closed_form`, `envelope`, `frozen_stall`, and `deflated_modal`, each adding one technique to the one before so that the techniques can be compared. `LTIVer1Solver` to `LTIVer5Solver` default to one preset each and keep the names the runners and the scripts use, and `LTIVer5Solver`, the `deflated_modal` preset, is the accelerated solver of the paper.

`solve()` resets the state as the core solvers do, runs one exact Dykstra cycle, builds the cycle map of the active set it found, and then runs episodes. An episode is a run of cycles with a constant active set, which the paper calls a phase. It ends in one of three outcomes, a switch at a given cycle, the end of the budget, or a settlement, and a switch is realised by one exact Dykstra cycle before the next episode starts. Within an episode the presets differ in how they get from one cycle to a later one: stepping through the cycle map, evaluating the closed form around its fixed point, jumping a run that an envelope bound certifies free of switches, fast-forwarding a stalling period, or scanning the deflated modal form of a singular episode. They also differ in how they settle. `cycle_map` never does, `closed_form` to `frozen_stall` settle on the fixed point once the active set is proven final, and `deflated_modal` alone tries the KKT certificate, at the episode entries its schedule chooses, at the limit of a singular episode, and wherever its active set is proven final, and settles only on a point that passes it. Without constraints `deflated_modal` settles at cycle 0 with the `"kkt"` certificate, since `z` is its own projection, as the KKT test proves with zero multipliers, unless its schedule is `"never"`. The other presets return the point unsettled in that case.

The state is the point and one scalar auxiliary per half-space, since Dykstra's correction for a half-space is always a multiple of its unit normal. Exact cycles write their history rows in `_exact_cycle`. A cycle the solver skipped is replayed from the previous row by `_record_cycle`, which is exact within an episode because an active half-space projects onto its boundary and an inactive one leaves the point alone. After a settlement `_record_limit` fills every remaining row with the limit.

The setting `schedule` decides at which episode entries `deflated_modal` tries the KKT test, and `KKTSchedule` in `lti_numerics.py` keeps its count. `"work"`, the default, tries the test at the first entry and afterwards only once the work done since the last failed entry test exceeds that test's work. Work is counted in flops, but only from sizes that the Python and the C share: the half-spaces, the touched coordinates, the active half-spaces of the episode, the candidate rows of a test, and the cycles an episode covers. Each covered cycle is priced as a Dykstra cycle whether it was evaluated or jumped, and an episode's setup is priced alike for both of its types. The split between evaluated and jumped cycles, the iterations of Lawson-Hanson, and near the cutoff the type of an episode can differ between the two languages, hence none of them enters, and both try the test at the same entries. The failed entry tests but the last therefore cost at most the rest of the work, and `kkt_record` holds both totals after a solve. The sums saturate at `WORK_CAP`, i.e. 2**63 - 1, in both languages. `"every"` tries the test at every entry and `"doubling"` at entries 1, 2, 4, 8, and so on. All three keep the tests at the limit of a singular episode and at a final active set, which the schedule does not decide and whose work neither resets the count nor adds to it. `"never"` runs no KKT test at all, so that a solve measures compaction alone and returns Dykstra's iterate at the budget.

The rule bounds the cost of the failed tests, not the delay of a settlement, since a test that passes at one entry need not pass at a later one, whose candidate rows differ. On the 120 dense problems of tab:dykvsacc, in C, `"work"` settles on the cycle of `"every"` on 87 problems and later on 33, and it makes a median of 0.47 of the KKT tests of `"every"` in 0.73 of its time to settlement. `"doubling"` settles later on 56, and on only 4 of the 20 problems of 252 x 64, against 10 under `"work"` and 12 under `"every"`. These figures come from the measurement of the three schedules with `performance_timing.py --schedule` on an Apple M5 Pro.

A solver built with `profile=True` keeps a `SolveProfile` through each solve and leaves its `as_dict()` in `solver.profile`. Each of the 14 stages of `STAGES`, from `exact_cycles` to `other`, is charged its exclusive wall time, its flops, and its entries, and `other` takes the time between stages, so that the times sum to the time of the solve. `COUNTS` holds the episodes by type, the exact, evaluated, skipped, and scanned cycles, the skipped cycles split by the jump that skipped them, the jumps and fast-forwards, and the KKT attempts and passes. Every KKT test leaves a record of where it ran, its candidate rows, the supports it verified and skipped, its least-squares solves, its flops with and without the memo, its time, and its verdict. `kkt_certificate`, `_kkt_verify`, `nonnegative_quadratic`, and `nonnegative_least_squares` add the flops of their products and solves to an optional `KKTTally`. `KKTMemo.costs` keeps the work of every support it remembers, hence `flops_without_memo` is the cost of the test without the memo, which the C does not keep. An unprofiled solve runs the same code, and each hook is then a test of `self._profile`. The schedule's count of work does not depend on the profile.

Within one solve a `KKTMemo` keeps the candidate supports derived from each set of candidate rows and the supports the KKT test rejected. Once `z` and the constraints are fixed, a verdict depends only on the support, so the memo changes neither the outcome nor the point. `solve()` runs under `ignore_blas_flags`, which ignores the floating-point flags that numpy 2.1.1 linked to Apple's Accelerate raises after products of finite matrices, and so do the oracle's entry points and the KKT and nonnegative least-squares functions.

`lti_numerics.py` holds the pieces that do not depend on solver state: the exact cycle, the cycle map and the prediction of the next active set from it, `touched_resolvent`, the closed forms, the finality test, the envelope horizon, the stalling-period crossing, Lawson-Hanson nonnegative least squares and its dual `nonnegative_quadratic`, and the KKT certificate. At its end come the flop counts of the profile, from `lstsq_flops` to `replay_flops` with `KKTTally`, and the schedule, from `SCHEDULES` to `KKTSchedule`.

### The C solvers

`C/accelerated.c` is the `deflated_modal` preset again, in C that depends only on `libm`, and `C/dykstra.c` is plain Dykstra, the baseline it is timed against. They exist for timing. The Python solvers allocate and fill a history on every cycle, which the C code does not keep, so each C solver returns only the final point, a status, a few counters, and the multipliers. `c_solvers.py` loads the built libraries from `C_FOLDER` through `ctypes` and validates the problem with `_validate_problem` first, because the C code checks neither shapes nor for NaN. It returns a `CSolverResult` with the projection, whether the solve settled, the cycles accounted for, and the multipliers. Its counters give the accelerated solver's exact cycles, episodes, switches, and jumps, its KKT tests and entry tests, the work its schedule counted, its power iterations, and `settled_at`, the cycle from which a settled result is the projection, as in `LTISolver`. `accelerated_c_projection` takes the same `schedule` as `LTISolver` and passes it to the C as its index in `SCHEDULES`. An empty constraint set is reported as settled at every budget, 0 included.

`accelerated.c` follows `lti_numerics.py` piece for piece, with the same rounding floors, cutoff, exchange in Lawson-Hanson, and KKT test, and departs from it in four places, each explained by a comment at that place.

1. A singular episode is scanned by iterating the contracting block `Q^T A_m Q` in the coordinates of the span, with envelope jumps, where the Python diagonalises that block and scans its modes in blocks. The sequence is the same, and an eigen-solver is not needed.
2. The condition number of `I - A_m` is estimated rather than computed. Its largest singular value lies between the Frobenius norm over the square root of p and the Frobenius norm, which decide the comparison with the cutoff unless they straddle it, and only then does a power iteration estimate it. It only chooses between episode types that trace the same path.
3. The least-squares solves inside Lawson-Hanson reuse a QR factorisation updated as rows enter and leave the support, and the loop stops as soon as an iteration leaves the solution unchanged, where the Python refactors each time and runs to its cap. The multipliers are the same.
4. The coordinates that are not touched by any constraint, called untouched below, are dropped before the solve and copied back into the result, in `solve_touched`, where the Python takes each episode decision on the touched coordinates. The decisions are the same.

An episode entry in C runs only the power iterations that decide something. The norm of the inverse of `I - A_m` is computed first, and the largest singular value only in the case of item 2. The contraction rate serves only envelope jumps, hence `skip_estimate` computes it at its first call in an episode whose inactive rows allow a jump, by the same routine from the same seed on the same matrix, and thus to the value an entry would have computed. On problems 0 to 4 of the tiers from 24 x 8 to 252 x 64 an entry runs a median of 10 to 48 power iterations, and `test_a_phase_entry_runs_few_power_iterations` in `tests/test_c_solvers.py` asks for fewer than 100 at 96 x 32 and 160 x 48.

Working storage comes from three blocks allocated once per solve, for the doubles, the ints, and the flags, after a problem with untouched coordinates has been copied without them. A scratch array is never shared between a stage and one that can run while its contents are still needed.

## 5. The result object

`solve()` always returns a `ProjectionResult`. `projection` and `path` are always populated. `settled_at` and `certificate` are `None` unless an LTI solver settled, and the other fields are `None` unless the matching constructor flag was set.

| Field | Flag | Shape |
|---|---|---|
| `projection` | always | `(dim,)` |
| `path` | always | `(max_iter + 1, constraints, dim)` |
| `squared_errors` | `track_error` | `(max_iter + 1,)` |
| `stalled_errors` | `track_error` | `(max_iter + 1,)`, `nan` where not stalled |
| `converged_errors` | `track_error` | `(max_iter + 1,)`, `nan` where not converged |
| `errors_for_plotting` | `plot_errors` | `(max_iter, constraints, dim)` |
| `active_half_spaces` | `plot_active_halfspaces` | `(constraints, max_iter + 1)` |
| `settled_at` | LTI solvers that settle | cycle, or `None` |
| `certificate` | LTI solvers that settle | `"kkt"`, `"finality"`, or `None` |

Note the transposition: `active_half_spaces` is constraint-major, and every other array is cycle-major.

`squared_errors`, `stalled_errors`, and `converged_errors` partition the same sequence three ways, so that a plot can colour each cycle by regime. `_track_error` stores the exact squared distance to the reference. It calls a cycle converged when that distance is below `min_error`, and otherwise stalled when it repeats the previous cycle's to within `RELATIVE_TOLERANCE` of the larger of the two, and a stalled cycle in this sense is an approximate stall in the paper's terms. Being relative, the classification depends neither on the scale of the problem nor on an untouched coordinate. `min_error` is an absolute threshold that only classifies cycles and never stops a run, so a problem scaled by `s` keeps its classification only with `min_error` scaled by `s**2`.

The flags are opt-in because the arrays are the expensive part: `path` and `errors_for_plotting` are both cycles by constraints by dimension.

Use the `has_error_tracking`, `has_error_plotting_data`, and `has_active_halfspace_data` predicates at a call site rather than testing a field against `None`, and `is_settled` for the settlement.

An LTI result is Dykstra's iterate after `max_iter` cycles, with the same path, errors, and corrections cycle for cycle, unless it settled. A settled result is the limit from `settled_at` on, in the result and in every history row. `active_half_spaces` means something slightly different for the two families. The core solvers test each half-space at the cycle's end point shifted by its correction, as if it were visited first, while the LTI solvers record the set that was active during the cycle.

## 6. Visualisation and export

The three visualiser classes are not interchangeable. `Visualiser` lays the half-space panels out horizontally. `VerticalVisualiser` subclasses it and puts the activity traces on a lower axis, for problems with more constraints than fit across. `ComparisonVisualiser` is a separate class, not a subclass, and draws two solvers' results against each other: the shared projection panel, the error comparison, and the activity comparison. `paper_figure.py` uses it. The figures of the paper are drawn by the scripts of section 9 with matplotlib directly, in the paper's palette from `paper_figures.py`.

`ResultExporter.export` writes a sectioned CSV, not a table. The sections, in order, are `METADATA` (solver name, iteration count, dimension, constraint count, `settled_at` and `certificate` for a settled result, then any keyword arguments passed through), `INITIAL_POINT`, `FINAL_PROJECTION`, `CONSTRAINTS_A`, and `CONSTRAINTS_B`, then `PATH_HISTORY`, `SQUARED_ERRORS`, `STALLED_ERRORS`, `CONVERGED_ERRORS`, `ERRORS_FOR_PLOTTING`, and `ACTIVE_HALFSPACES` for whichever tracking was enabled. If `output_path` is a directory, the filename becomes `<solver_name>_<max_iter>_iterations.csv`. A `nan` of a cycle that is not stalled or not converged is written as a blank cell.

`ResultExporter.load` reads that back, reads a blank cell as `nan` in a float array, and reshapes the flattened path and error blocks to cycle by constraint using `num_constraints` from the metadata. It also accepts the legacy section names `CONSTRAINTS_N` and `CONSTRAINTS_C`, which predate the `A @ x <= b` naming, and `test_csv_loader_accepts_legacy_constraint_sections` holds it to that.

`paper_figure.py` writes its CSV files to `results/` under `REPOSITORY_ROOT`, whatever the working directory.

## 7. Numerical contracts

Normals need not be of unit length, since `_normalise` scales each row and its offset together before use. Callers may pass whatever the geometry gave them.

Validation is strict and happens once, in `_validate_problem`, which copies its inputs so that a caller's arrays are never mutated. `ValueError` is raised for a `z` that is not a nonempty 1-D point, an `A` that is not 2-D, a `b` that is not 1-D, a row count mismatch between `A` and `b`, a normal whose width is not `z.size`, any nonfinite entry, a zero-norm normal, an explicit `dimensions` that disagrees with `z.size`, a `max_iter` that is not a nonnegative integer, and a `min_error` that is nonfinite or negative. Booleans are rejected where an integer is required. An empty constraint set is legal, and the core solvers return the point unchanged.

The reference projection is computed once in the constructor by `_find_optimal_solution`. A point that satisfies every row is returned as itself. Otherwise the QP is solved over the coordinates some constraint touches, and the others keep the point's value. quadprog rounds every coordinate in its unconstrained step, and without these two rules a feasible start would come back one unit in the last place away, while an untouched coordinate of 1e8 would lose its last bit. The QP's matrices are formed without matmul, which numpy 2.1.1 linked to Accelerate flags with spurious warnings from size 16 up. Rounding limits the reference when active normals are nearly dependent: for two normals 1e-10 apart through a vertex, the squared distances of the vertex and of the projection onto one boundary alone are equal in double precision, and quadprog cannot tell them apart. quadprog also rejects some feasible polyhedra that are a single point as inconsistent, so a Python solver cannot be built for them.

The reference is otherwise exact, and Dykstra at finite `max_iter` generally is not. Every error number in this repository and in the paper is a squared distance to the quadprog solution rather than to an idealised limit. A result is described as "the projection" only with the cycle count that produced it, or with a `"kkt"` certificate.

The core solvers' tolerances are relative. `_track_error` and `_beta_check` compare against `RELATIVE_TOLERANCE` of the magnitudes involved, and the stall detection solver compares each output with a rounding floor of 64 eps times the magnitudes summed in its visit.

The LTI solvers compare quantities that are zero in exact arithmetic, such as a drift, a slack, or an increment, against a rounding floor of 64 eps times the magnitudes that were summed to form them, never against an absolute constant. Neither the problem's scale nor an untouched coordinate may change a decision. An untouched coordinate makes the full `I - A_m` singular, because `A_m` is the identity on it, hence every episode decision is taken on the touched coordinates. `cycle_map` marks them and zeroes the span outside them, the condition number comes from `touched_resolvent`, i.e. `I - A_m` on the touched coordinates, the closed forms solve on the touched block and keep the untouched coordinates of the point, and the envelope's contraction rate comes from the touched block of `A_m`. The closed form is used only while that condition number is below `1e8`, and beyond it an episode is stepped or deflated. A stationary state means a state fixed to rounding, coordinate by coordinate. `is_frozen` compares the motion of a cycle with the rounding floor of `|A_m| |x| + |B_m| + |x|`, except that a cycle mixes the coordinates its active normals touch into one another. Each of those coordinates is therefore charged with the largest of their magnitudes, which `CycleMap.coupled` marks, while a coordinate that no active normal touches does not move at all. A floor charged with every magnitude the cycle adds instead would hold a slow drain of `5.7e-14` per cycle as stationary, and `test_modal_scan_drops_a_real_drain_where_dykstra_does` fails on it.

The first candidate support of the KKT certificate comes from `nonnegative_quadratic`, the dual of projecting `z` onto the candidate rows, whose Gram matrix is singular whenever there are more candidate rows than dimensions. When a row enters dependent on the support, i.e. least squares finds the support's Gram block rank-deficient with a residual beyond rounding, the multipliers move along that residual until the first one it lowers reaches zero, and that row leaves the support. This is the exchange that Goldfarb and Idnani's dual method makes. The exchange is triggered by the rank rather than by the residual alone, because an ill-conditioned support of full rank can leave a residual beyond a componentwise floor that is still rounding. A row entering with a zero gap takes a step ratio of 0.

The KKT certificate accepts a point only if it is feasible and complementary at rounding level, and if its stationarity residual, which bounds its distance to the projection, is within `1e-9` of the step from `z` beyond rounding. Least squares spreads its rounding over every coordinate a support row touches, on the scale of the whole correction, however little the step moves that coordinate. The floors of feasibility and complementarity therefore charge each such coordinate with the norm of the correction, and the stationarity allowance adds the norm of the step on every coordinate a tight row touches. The multiplier terms enter only at rounding, since they grow as the tight normals become nearly dependent. A `"kkt"` result is therefore the projection to that accuracy. Rounding limits it when the tight normals are nearly dependent, since their multipliers are then large, and when the step is small beside the coordinates of `z` and the point, as for a starting point close to constraints far from the origin. A `"finality"` result is weaker: a drift below rounding counts as zero, so a decrease slower than rounding can make the active set look final when it is not.

## 8. Testing strategy

The suite runs from the repository root with one command, `.venv/bin/python -m unittest discover -s tests`, and holds 268 tests in nine files. The counts below come from loading each file with unittest.

- `tests/test_solver_unit.py` (9 tests) covers the geometry primitives and input validation: projection of a feasible point, a nonunit normal, and each rejection path.
- `tests/test_solver_regressions.py` (18 tests) holds a regression test for each defect fixed in the core solvers, `edge_rounder.py`, and the reference projection. Constraints already satisfied at the start are retained, the dimension is inferred from the point, zero iterations still record the initial error, and a fast-forwarded run matches plain Dykstra at the corresponding cycles, including outputs that jitter, a skip count at a tie, and a single repeating visit or a converged fixed point that must not trigger a jump. Squared errors keep their value at small scales, the stall classification does not change with the scale, the hybrid switches to Dykstra's corrections on a boundary, the deprecation warning gives the caller's line, and a second solve gives the same result. A feasible start is its own reference, an untouched coordinate keeps its value in the reference, constructing a solver in 16 dimensions does not raise a floating-point warning, and a rounded box that is not square contains every point of the box. New bug fixes of the core solvers belong here, test first.
- `tests/test_visualiser_regressions.py` (4 tests) covers layout scaling past three constraints and CSV round-tripping, including the legacy section names and blank errors read back as `nan`.
- `tests/test_stress_core.py` (28 tests) is a seeded battery of the core solvers against quadprog. Its random polyhedra follow the law of Generator 2 and range from 2 to 64 dimensions and from 3 to 200 half-spaces, and it adds nearly dependent normals, redundant and rescaled rows, feasible starts, invariance under scaling and under an untouched coordinate, the stall of the box and line, edge cases, the paper's examples, and an export round trip. `BitwiseReferenceTests` holds every output of the three solvers on 52 problems, the printed log included, to the digests in `tests/core_solver_reference.npz`, and skips on any platform but macOS arm64 with numpy 2.1.1 on Accelerate. `RepeatedWorkTests` counts calls to show that each row is normalised once per solver and that activity is tested only for a plotted record.
- `tests/test_lti_solvers.py` (81 tests) covers the LTI solvers and the oracle, and is where their regressions belong, test first. Most tests state the contract rather than an implementation: the Dykstra iterate at the same budget or, once settled, the projection, a history equal to Dykstra's up to the settlement, and invariance under scaling the problem and adding untouched coordinates. The few tests that count exact cycles or stepped cycles do so because the defect they target is lost acceleration rather than a wrong point. `LTIOverheadTests` checks under the schedule `"every"` that the KKT memo changes neither the settlement cycle nor the result. `FrozenFloorTests` holds a stalling state of the stall family stationary on every cycle of its stall. `KKTScheduleTests` checks the bound of `"work"` on the 96 x 32 problem of fig:performance, where `"every"` breaks it, the projection certified under every schedule, the entries of `"doubling"`, the iterate of `"never"` at every budget, and the setting itself. `LTIProfileTests` holds a profiled solve bitwise to an unprofiled one on runs that enter every stage but `other`, and checks that the exact, evaluated, and skipped cycles add up to the cycles run, that the flops of a KKT test without the memo are those of a solve without one, and that `profile` is a flag. Some checks are not reached by any problem in the suite, such as the kernel projection of the deflated solve, because the suite does not contain a singular episode ill-conditioned enough for rounding to move the kernel component measurably.
- `tests/test_stress_lti.py` (11 tests) is a seeded battery of the LTI solvers, the oracle, and the C solvers. Every preset follows Dykstra or certifies on random polyhedra up to 200 rows in 64 dimensions and on degenerate arrangements. The dual reaches quadprog's projection on 3000 small systems, and the certificate accepts the projection given its support on 6000. It also checks starts inside the polyhedron, scaling by 1e-6 and 1e6 and an untouched coordinate for every preset and both C solvers, every prefix of a recorded oracle schedule, the C solvers against the Python at every budget, the paper's examples, and the 96 x 32 problem of fig:performance, certified at cycle 551 while Dykstra still moves. It rebuilds its problems without importing pyplot.
- `tests/test_c_solvers.py` (17 tests) holds the C solvers to the same contract through `c_solvers.py`, and is skipped until the libraries are built. Without a history to compare, the path is checked by solving at every budget: an unsettled result must be Dykstra's iterate there and a settled one the projection. It also checks plain Dykstra's points and corrections against the Python, invariance under scaling and under an untouched coordinate, the KKT conditions of the multipliers, and the regressions shared with the Python. `CScheduleTests` holds the C to the Python under all four schedules on 13 problems, in its tests, entry tests, work, settle cycle, and point, and checks the bound of `"work"` in C, the iterate of `"never"` at every budget, the validation of the setting, and the power iterations of an episode entry.
- `tests/test_paper_outputs.py` (93 tests) covers the figure and table scripts: the vertex floors, loop residuals, shedding cycle, and envelope crossings labelled in the figures, the generators and the wedge and stall families, a certified `LTIVer5Solver` result against the reference, the run-to-tolerance timing with its quartiles, its schedules, the budget of its certified column in each implementation, and the records it keeps of another implementation, the generated `.tex` files, the square-and-line example, the C validation and its settle cycle, the benchmark's options and a short run of each family, the cost model, the compaction-only study, the activity recorder and its counting convention, both exact counterexamples of the activity-change study, the stall detectors and families, the stall grid's matrix plots, the contraction rates of the angle study, the rank deficiency and the norm of T of the singular-phase study, the totals of the oracle comparison, and a quick run of each figure study and of these two into a temporary directory.
- `tests/test_package_layout.py` (7 tests) checks the package itself. Every module imports from the root in a fresh interpreter without changing `sys.path`, the C libraries and the outputs are found under `REPOSITORY_ROOT` from any working directory, and eight of the figure and table scripts run under `python -m` with `--quick`, write their named outputs into a temporary directory, and leave `results/` unchanged.

The suite runs without a package install, a `conftest.py`, or pytest. Tests that depend on the C libraries or the benchmark group are skipped without them, and with both present the suite skips none. `tests/test_visualiser_regressions.py` selects Agg before importing pyplot. `tests/test_solver_unit.py` and `tests/test_solver_regressions.py` never import pyplot, and `tests/test_lti_solvers.py` imports it only through `visualiser` in its export test, which does not draw anything. `tests/test_paper_outputs.py` imports it through `paper_figures`, which selects Agg first, and the quick runs of `tests/test_package_layout.py` start with `MPLBACKEND=Agg`.

## 9. The paper

The paper's LaTeX sources are kept outside the repository. The repository holds the scripts that compute every figure and table drawn from data in the paper and the supplement, listed in `AGENTS.md` with the command for each. Each script writes into `results/paper` under `REPOSITORY_ROOT`, which git ignores, and prints every number quoted in the paper from its outputs. A figure is written as a PNG and a PDF in the paper's palette, which `paper_figures.py` defines, and, for the figures the supplement includes, under the basename it includes them by. A figure that the paper draws with TikZ or pgfplots is also written as that code with its coordinates, `fig-<label>.tex`, and table rows as `tab-<label>.tex`. The article includes no PDF, since its figures are drawn from those files, and the supplement includes thirteen PDFs, which `AGENTS.md` lists. Each `.tex` file opens with a comment giving the command that generated it. Every parameter not stated in the paper is a named constant at the top of its script, with a comment saying the value was chosen there.

`problem_generators.py` holds the two generators of the supplement and the two structured families of the benchmark. Generator 1, `RandomTestPlanes`, rejection-samples bounded nonempty polyhedra and certifies each draw with linear programs through scipy. Generator 2, `BoundedTestPlanes`, constructs one directly from a positively spanning set of rotated normals and an interior anchor. `problem(num_planes, num_dimensions, seed)` returns `(A, b, z)` from Generator 2 with an infeasible start, and `problem_seed(num_planes, index)` gives problem `index` of a size tier its seed. `WedgeTestPlanes` and `BoxSlabTestPlanes` are the benchmark's structured families. The first is the wedge of the angle sweeps, which `stall_angles.py` imports, and the second the square-and-line example lifted to p dimensions, on which Dykstra's algorithm stalls. Their `problem(seed)` draws the polyhedron, its rotation, and its start from one seeded stream. None of the classes normalises its rows, since the law of the normals is stated for the rows as drawn.

The general-purpose QP solvers of `benchmark.py` are called through qpsolvers with the options qpbenchmark 2.7.1 sets, and they are installed only with the dependency group named benchmark, so that a plain `uv sync` stays small. `benchmark.py` runs them, the C solvers, and the oracle on three families, the dense tiers of Generator 2, the wedge, and the stall family, which `--family` chooses. `performance_timing.py`, `benchmark.py`, `cost_model.py`, and `oracle_comparison.py` print the machine, the operating system, the Python, numpy, and quadprog versions, the C compiler and its flags, and a line stating the timing method, before their results. In the first two and in `oracle_comparison.py`, each time is the median of runs repeated until they total 0.5 s or number five, and in `cost_model.py` the median of at least five runs, continued until they total 0.2 s or number 200. The C solvers are timed as whole calls, and the Python solvers in `solve()` alone, because their constructor runs the quadprog reference solve. `performance_timing.py` times problems 0 to 19 of each tier, and every cell of its tables reads the median with the first and third quartiles. After a settlement a Python LTI solver writes the limit into every remaining row of its history, which is not the algorithm's work. The certified column of `performance_timing.py` therefore times a run cut at the settle cycle plus one, which an untimed run of the same implementation within 20000 cycles finds, or a run of 20000 cycles where the solver does not settle.

The accelerated solver wins in cycles and not in wall time on the random families. In the C table that a full run of `performance_timing` writes on an Apple M5 Pro, its median at 96 x 32 reaches squared error 1e-3 after 562 cycles against Dykstra's 2143, yet in 9.15 ms against 2.89 ms, and at 252 x 64 it takes 300 ms against Dykstra's 26.0 ms. The reason is the cost of an episode, i.e. its cycle map, its setup, and, at the entries the schedule chooses, the KKT test. In the table of `cost_model.py` a C episode costs 41 to 247 C Dykstra cycles beyond its exact cycle on the six tiers from 12 x 4 to 252 x 64, while it covers 0 to 108 cycles beyond it, medians over twenty problems per tier. No episode of these tiers thus repays its cost by skipping cycles, and the solver wins only by settling, which replaces the remaining Dykstra cycles at once. On the wedge and stall families the KKT test certifies the projection at the first episode entry, after one cycle, on every problem of `benchmark.py`, and there the C accelerated solver is faster than C Dykstra. Its median time in the headline table of `benchmark.py --family all` is 0.013 ms against 1.26 ms on the wedge family and 0.0136 ms against 0.0363 ms on the stall family. These timings come from full runs of the three scripts on an idle Apple M5 Pro.

`singular_phases.py` counts the singular phases, those whose active normals do not span R^p, an empty active set included, with their shares of the phases and of the cycles. For every other phase it reads the 2-norm and the spectral radius of T = Q^T A_m Q, the cycle map on the span of the active normals, where Q is the span that `cycle_map` returns. On every phase it checks that the rank deficiency of Q equals the unit eigenvalues that `activity_study.span_eigenvalues` leaves out. The phases are those of the activity study's curve battery, recorded with that study's `draw_problem`, `record_runs`, and seeds, and those that `oracle.record_schedule` records over the first 3000 cycles of problems 0 to 4 of the dense tiers of tab:dykvsacc. The battery's phases are counted from cycle 1 on, as the study counts those of fig:am_eigs, hence a run whose active set in cycle 1 is the set of half-spaces z violates has its first phase left out. In a full run, 2350 of the 33171 phases of the battery are singular, 7.1%, and 41 of the 1590 phases of the dense tiers, 2.6%, which hold 11.6% of their cycles. The largest norm of T is 1 - 7.1e-10 on the battery and 1 - 2.1e-6 on the dense tiers, hence below the cap of 1 - 1e-12 that the C places on its estimate of the contraction rate.

`oracle_comparison.py` sets the oracle against the Python accelerated solver on the dense problems of `benchmark.py`. C Dykstra and the oracle run through `benchmark.run_projection_method`, hence the oracle solves the problems on which C Dykstra settles within 1e6 cycles, and its work is counted as its episodes, each entered by one exact cycle, and the closed forms it evaluates. `LTIVer5Solver` takes its counts from a profiled solve within 1e5 cycles. After a settlement the Python solver writes the limit into every remaining history row, which within 1e5 cycles can take most of the time of a solve, hence it is timed at its settle cycle plus one, where it follows the same path. In a full run on an Apple M5 Pro, 33 of the 45 problems are solved by both, on which the oracle takes 0.50 s in total and the accelerated solver 2.1 s, and the median ratio of their times per problem is 1.1, from 0.44 to 13. The oracle replays every cycle to Dykstra's fixed point, while the accelerated solver stops at its certificate, after a median of 11 cycles, which makes its median time the smaller of the two on the tiers 12 x 4, 20 x 6, and 36 x 10.

`paper_figure.py` is not part of the SIAM paper. It draws the comparison figure of an earlier report, a box with a line through it projected from `(-2, 1.4)` over 30 cycles, `DykstraProjectionSolver` against `DykstraStallDetectionSolver`, and writes `Dykstra_30_iterations.csv` and `Algorithm (1)_30_iterations.csv` to `results/`.
